# Koko eating bananas discussion

## Initial thoughts
I had quite a few attempts at this one and found it exceedingly difficult. There are a couple of versions of the brute force here. You can either approach it from the perspective of trying every single possible answer and moving through the entire array checking if it is true or you can try and do a more heuristic approach by sorting the array and coming from one end of it attempting to remove the larger values as you go. This was really my first attempted approach at this. I did see that the approach was fundamentally flawed in a couple of ways though such as if you have an array full of the same values you then have to backtrack all across the array keeping a log of how many hours each "Same" value requires to complete. I also considered ways of doing this using a logging system that logs occurences of the same variable again and again so the above calculation can be done quicker if necessary.

Essentially all these implementations were flawed and either worked in terrible time complexity, only partially worked or they were so overly complex as to be a nest of unreadable code that was near impossible to keep track of. After a few of these attempts I decided to look up the concept behind the answer and then implement it myself because I was very clearly missing something.

## minEatingSpeed
So this is the solution that I found and it turns out it sort of is a completely different way of thinking about the question. So it inverts the use of a binary search where we instead use a combination of brute force and binary search. We use the binary search through all of the possible answers if we find that the eating speed is too slow we move right if we find that the answer is too fast we move left and every time we do a brute force through the array checking if we will be able to eat the bananas in time with early exits if we have gone over the amount of time. We end up with O(nLog(maxPileSize)) Time complexity and O(1) space complexity.

## Thoughts
For the first time I am not annoyed that I didn't get this question alone. I think it has been a great learning experience to get this one wrong and have a completely different perspective on it. I don't want my coding skills to go dull but there comes a point where if you are not looking up an answer you are sort of just wasting time and mental resources, I just have to remain disciplined that it does not become a crutch. 

I did think of a few other things to do with this that are somewhat interesting. If the data came presorted we could probably optimise the early exit by iterating the larger values first as they are more likely to create an early exit. There would also be situations where we could take the size of the array against the size of possible answers and use the brute force approach instead because it would be more effective to traverse the array than binary check all the answers but since they are edge cases and it would over complicated (and it was already taking longer than expected) I did not implementing, but it is an interesting thought experiment nonetheless. I actually think its very interesting that for a lot of the questions that are larger than O(N) complexity we could possibly do sweeps of the data to check certain things (because a lot of the time we might be doing that early) and do a selective algorithm based on that information.
