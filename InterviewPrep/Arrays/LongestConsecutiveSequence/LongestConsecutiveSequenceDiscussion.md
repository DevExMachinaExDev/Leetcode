# Longest consecutive sequence discussion.

## First instincts

I always like questions like this simply because they strip away all of the unnecessarily confusing wording and they just take a seemingly simple problem and hand it over to you. The hardest part of this is of course making it run as quickly as possible.
My first thought here was that some kind of bucket sort could be used then you traverse the length of the bucket counting the largest consecutive run as you go. Whilst this might have worked it turns out that the constraints are too large for the memory usage to be viable for this problem. My next thought was that it must require a hashmap of sorts, because we cannot know the order until it is either sorted (which would violate the O(N) time scale) or stored in another data structure. A sorted hash map is also out for the same reason of not being O(N) timescale. I  then realised that a standard unsorted hashmap would be overkill for this problem because we are not interested in elements that are the same and also we do not require key value pairs as such just the values themselves for lookup which put me onto the path of using an unordered set. Then i came up with the solution.


## longestConsecutive

The concept of the algorithm is simple. First we populate the set with all the unique values. this makes it easier to lookup if a value exist with a hash lookup. Next we loop through the set and look for values that are at the start of a sequence, this is achieved by checking if the hash value before this on exist or not. If it does not we then do an inner loop to check how long the sequence runs for. At this stage in my original design I had it remove the elements it found, but the logic seemed to be slower in testing and added convuluted unmaintainable code so it was removed from the final solution which might sometimes check the same value twice on the inner and outer loop. I suspect this may have been due to the hash table having to be reorganised periodically or perhaps something that confused the branch prediction.At first glance this solution looks suspicious because it contains a nested loop which would normally suggest O(n^2) complexity. However the inner loop only runs when a value is the start of a sequence. Values that are already part of a sequence cannot start a new one because the previous value exists in the set. As a result each value is only really processed once as part of a consecutive run, meaning the total amount of work still grows linearly with the input size and the algorithm remains O(n).

## Additional ideas for this
Besides a bucket sort we could of course just brute force this solution for the minimal memory solution with the massive tradeoff for having to check the entire array for a consecutive element every time. I think that the most simple solution would be the one the problem is trying to forbid of just using a sort and then counting from there but other than that i see little else of note or value to attempt.
